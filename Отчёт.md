# BondMap — Отчёт

Учебное клиент-серверное приложение для курса SRE/DevOps.  
Используется как базовое приложение для последующих домашних заданий.

---

## 1. Доменная область

**BondMap** — приложение для анализа облигаций.

Пользователь может:

- просматривать список облигаций;
- изучать параметры выпуска (тикер, номинал, купон, дата погашения, валюта, период купона);
- просматривать историю цен;
- рассчитывать текущую доходность;
- искать и фильтровать облигации по параметрам (валюта, диапазон доходности, сортировка).

Взаимодействие: **Android-клиент → HTTP REST API → PostgreSQL**.

Backend — самостоятельный HTTP-сервис. Frontend не содержит бизнес-логики хранения данных.

---

## 2. Стек реализации

### Backend

| Технология | Роль |
|---|---|
| Kotlin | язык |
| Spring Boot | каркас приложения |
| Spring Web (MVC) | HTTP REST API |
| Spring Data JPA | доступ к данным |
| PostgreSQL | СУБД |
| Flyway | миграции схемы |
| Gradle (Kotlin DSL) + Wrapper | сборка и зависимости |
| springdoc OpenAPI | Swagger UI |
| Docker / Docker Compose | сборка образа и запуск окружения |

### Frontend

| Технология | Роль |
|---|---|
| Kotlin | язык |
| Jetpack Compose | UI |
| Retrofit + OkHttp + Gson | HTTP-клиент к API |
| MVVM (ViewModel + StateFlow) | архитектура экранов |
| Android Gradle Plugin | сборка клиента |

### Почему HTTP

Взаимодействие с backend идёт по **HTTP/JSON**, а не gRPC — это упрощает последующие задания по балансировке трафика и отладке через обычные HTTP-инструменты (Swagger, curl, браузер).

## 3. Основные сущности доменной области

### Bond (облигация)

| Поле | Описание |
|---|---|
| `id` | идентификатор |
| `ticker` | биржевой тикер |
| `isin` | ISIN выпуска |
| `name` | название выпуска |
| `bondType` | тип: GOVERNMENT / CORPORATE / EUROBOND / MUNICIPAL |
| `nominal` | номинальная стоимость |
| `couponRate` | купонная ставка, % годовых |
| `maturityDate` | дата погашения |
| `currency` | валюта |
| `couponPeriodDays` | период выплаты купона, дни |

### BondPrice (история цены)

| Поле | Описание |
|---|---|
| `id` | идентификатор |
| `bond` / `bond_id` | связь с облигацией |
| `price` / `closePrice` | цена закрытия |
| `openPrice` / `highPrice` / `lowPrice` | OHLC (учебная симуляция) |
| `volume` | объём |
| `priceDate` | дата котировки |
| `source` | источник (`SIMULATION`) |

### KeyRate (ключевая ставка, учебный ряд)

| Поле | Описание |
|---|---|
| `id` | идентификатор |
| `rate` | ставка, % |
| `rateDate` | дата значения |

### CRUD и связанные операции (HTTP)

| Метод | Путь | Операция |
|---|---|---|
| `GET` | `/api/bonds` | список (Read) |
| `GET` | `/api/bonds/{id}` | чтение по id (Read) |
| `POST` | `/api/bonds` | создание (Create, 201) |
| `PUT` | `/api/bonds/{id}` | обновление (Update) |
| `DELETE` | `/api/bonds/{id}` | удаление (Delete, 204) |
| `POST` | `/api/bonds/{id}/prices` | добавить цену |
| `GET` | `/api/bonds/{id}/prices` | история цен |
| `GET` | `/api/bonds/{id}/details` | детали выпуска |
| `GET` | `/api/bonds/{id}/yield` | расчёт доходности |
| `GET` | `/api/bonds/{id}/analytics` | YTM, дюрация, спред |
| `GET` | `/api/bonds/{id}/scenario` | шок доходности |
| `GET` | `/api/bonds/search` | поиск / фильтрация |
| `GET` | `/api/key-rates` | история ключевой ставки |
| `GET` | `/health` | проверка живости процесса |

Полный CRUD реализован для сущности **Bond**. Для **BondPrice** и **KeyRate** — создание и чтение (история котировок и ставок).

Swagger UI: `http://localhost:8080/swagger-ui/index.html`

Автотесты: `bondmap-backend` — `./gradlew test` (CRUD API, поиск, калькулятор YTM/дюрации). Android-клиент — `frontend/gradlew test` (форматирование, DTO, фильтр графика).

## 4. Соответствие методологии Twelve-Factor App

Ниже — аргументация **по каждому пункту** с привязкой к реализации BondMap.

### I. Codebase — один репозиторий

**Соответствует.**

Один codebase приложения:

```text
bondmap/
├── Отчёт.md
├── README.md
├── bondmap-backend/   ← backend (Spring Boot)
└── frontend/          ← Android-клиент
```

Нет отдельных веток/копий кода «для prod» и «для dev». Различия окружений задаются конфигурацией, а не форками репозитория.

### II. Dependencies — явные зависимости

**Соответствует.**

- Backend: все зависимости объявлены в `bondmap-backend/build.gradle.kts`. Сборка через Gradle Wrapper (`gradlew` / `gradlew.bat`) — не требуется вручную ставить библиотеки в систему.
- Frontend: зависимости объявлены в `frontend/build.gradle.kts` и `frontend/app/build.gradle.kts` (Compose, Retrofit, Navigation и т.д.). Разрешение зависимостей выполняет Gradle / Android Studio из деклараций проекта, без ручной установки JAR в ОС. Unit-тесты клиента — JUnit на JVM (`./gradlew test`), без эмулятора.

### III. Config — конфигурация вне кода

**Соответствует.**

Параметры окружения вынесены из исходников:

| Переменная | Назначение |
|---|---|
| `PORT` | порт HTTP-сервиса |
| `DATABASE_URL` | JDBC URL PostgreSQL |
| `DATABASE_USERNAME` | пользователь БД |
| `DATABASE_PASSWORD` | пароль БД |
| `API_BASE_URL` | URL backend для сборки Android-клиента |

Реализация: `bondmap-backend/src/main/resources/application.yml` читает значения из env.  
Образец — `bondmap-backend/.env.example`. Файл `.env` с секретами **не** коммитится (указан в `.gitignore`).

Android-клиент читает `BuildConfig.API_BASE_URL`. Значение задаётся при сборке переменной окружения `API_BASE_URL` или Gradle `-PAPI_BASE_URL=...`; по умолчанию `http://10.0.2.2:8080/` (localhost хоста с эмулятора). Сетевые вызовы не содержат захардкоженный хост.

В Git не хранятся боевые пароли и адреса БД как единственный источник истины.

### IV. Backing services — ресурсы как подключаемые сервисы

**Соответствует.**

PostgreSQL — внешний backing service. Backend получает URL и учётные данные только из конфигурации.  
В Docker Compose БД — отдельный сервис `postgres`; приложение подключается к `jdbc:postgresql://postgres:5432/...`.  
Замена хоста/порта/имени БД не требует изменения Kotlin-кода.

### V. Build, release, run — строгое разделение стадий

**Соответствует.**

1. **Build** — `./gradlew bootJar` (компиляция и сборка JAR). В Docker это этап `build` Dockerfile.  
2. **Release** — Docker-образ backend (`docker compose build` / образ с JAR + env).  
3. **Run** — запуск контейнеров `docker compose up` с переменными окружения.

Один и тот же артефакт (JAR/образ) запускается с разным конфигом (dev/demo), без пересборки под каждое окружение.

### VI. Processes — stateless-процессы

**Соответствует.**

Backend не хранит пользовательские сессии и бизнес-состояние в памяти процесса.  
Все устойчивые данные — в PostgreSQL. Процесс можно остановить и заменить другим экземпляром без потери данных приложения.

### VII. Port binding — самодостаточный HTTP-сервис

**Соответствует.**

Приложение само слушает HTTP-порт (`server.port: ${PORT:8080}`) и отдаёт REST API.  
Не требует отдельного контейнера приложений «внутри» внешнего app-server для базового запуска: достаточно JVM/контейнера. Снаружи порт пробрасывается Docker Compose (`8080:8080`).

### VIII. Concurrency — масштабирование процессами

**Соответствует.**

Масштабирование планируется горизонтально: несколько экземпляров backend за балансировщиком (для последующих ДЗ).  
Это возможно, потому что процесс stateless (см. VI): нет локального состояния, привязанного к одному инстансу.

### IX. Disposability — быстрый старт и корректное завершение

**Соответствует.**

- Старт: контейнер/JAR поднимается как обычный Spring Boot-сервис с миграциями Flyway.  
- Остановка: `server.shutdown: graceful` и таймаут фазы shutdown в `application.yml` — корректная обработка SIGTERM в Docker.  
- Для оркестрации есть `GET /health` и healthcheck в Dockerfile / Compose.

### X. Dev/prod parity — максимальное сходство окружений

**Соответствует.**

Локально и в «учебном проде» используются:

- одна и та же СУБД PostgreSQL 17 (`postgres:17` в Compose);
- один и тот же способ поставки backend (Docker-образ / тот же JAR);
- одни и те же миграции Flyway.

Docker Compose сближает окружения и уменьшает эффект «у меня локально работало».

### XI. Logs — логи как поток событий

**Соответствует.**

Приложение пишет логи в **stdout/stderr** (стандартное поведение Spring Boot в контейнере).  
Отдельные log-файлы внутри контейнера не создаются. Сбор и анализ логов — задача среды исполнения (Docker logs / последующие ДЗ по логированию).

### XII. Admin processes — админ-задачи отдельно

**Соответствует** (с уточнением).

- Изменение схемы БД оформлено как **версионируемые миграции Flyway** (`src/main/resources/db/migration/`), а не ручные правки «на лету» из UI.  
- Обслуживание PostgreSQL (backup, psql, one-off SQL) выполняется отдельными административными действиями, не через request-path бизнес-API.

Уточнение: миграции применяются при старте приложения (`spring.flyway.enabled=true`). Для учебного стенда это допустимо и воспроизводимо; в более строгой prod-модели миграции можно выносить в отдельный one-off job — архитектура миграций (SQL в репозитории) к этому уже готова.

## 5. Архитектура (кратко)

```text
Android (Compose + Retrofit)
        │  HTTP/JSON
        ▼

        │
        ▼
   PostgreSQL
```

Слои backend: `controller` → `service` → `repository` → БД.

## 6. Как запустить (для проверки)

### Backend

```bash
cd bondmap-backend
cp .env.example .env   # при необходимости
docker compose up --build
```

Проверки:

- http://localhost:8080/health → `OK`
- http://localhost:8080/swagger-ui/index.html
- http://localhost:8080/api/bonds

### Frontend

1. Backend должен быть запущен.  
2. Открыть каталог `frontend` в Android Studio.  
3. Запустить на эмуляторе (API: `http://10.0.2.2:8080/`).

Подробнее: `bondmap-backend/README.md`, `frontend/README.md`.
